Edit Food Log

Created: 2026-06-10 · Status: Draft · Mockups: Edit Page · Diary View

1. Problem Statement

Users cannot edit food logs after creating them. If they log incorrect nutrition data, wrong meal type, or a food from the wrong date, they must delete and re-log. Additionally, food logs cannot have photos, unlike weight logs which support photo uploads.

2. Goals

  • Enable editing of all food log fields via a dedicated page
  • Support photo upload/change on food logs
  • Display photo thumbnails in diary view for logs with photos
  • Maintain consistency with existing EditWeight patterns
  • Ensure users can only edit their own logs

3. Design Decisions

3.1 Approach: Dedicated Page

Following the EditWeight precedent, we use a dedicated page at /food/log/:id/edit rather than a modal or inline editing. This provides full-screen space for all fields and photo management.

3.2 Navigation: Tap Row

Tapping anywhere on a food log row navigates to the edit page. The delete button (✕) remains separate with stopPropagation to prevent navigation when deleting.

3.3 Photo Storage: FoodLog (Per Entry)

Photos attach to individual FoodLog entries, not to Food records. This avoids cross-user photo leakage on shared foods and allows different photos for the same food logged multiple times. Recent foods and search results derive photos from the user's latest log for each food via a join query.

3.4 Linked Food Update

When editing a log, the linked Food record's nutrition data (calories, protein, carbs, fat, serving_size) updates to match the log. However, other FoodLog entries referencing that food are not retroactively updated — each log preserves its own nutrition snapshot.

3.5 Date Editing

Users can change the date of a log, effectively moving it to a different day. The diary reflects this immediately.

5. API Changes

5.1 Existing Endpoints

MethodPathChange
GET/food/log/<id>Verify exists, ensure returns photo_url, number_of_servings, serving_size
PUT/food/log/<id>Accept new fields: number_of_servings, serving_size, photo_url

5.2 New Endpoints

MethodPathDescription
POST/food/log/<id>/photoUpload photo for food log. Accepts multipart form with photo field.
DELETE/food/log/<id>/photoRemove photo from food log. Deletes file from storage.

5.3 Security

All endpoints must verify FoodLog.user_id == current_user.id. Return 403 if user attempts to edit another user's log.

5.4 Recent Foods / Search Photo Derivation

When fetching recent foods or search results, include a subquery to get the latest FoodLog.photo_url for each Food, filtered by current user. Example:

SELECT f.*, sub.photo_url
FROM foods f
LEFT JOIN LATERAL (
  SELECT photo_url
  FROM food_logs
  WHERE food_logs.food_id = f.id
    AND food_logs.user_id = :current_user_id
  ORDER BY food_logs.created_at DESC
  LIMIT 1
) sub ON true
WHERE ...

7. Edge Cases

  1. Photo upload fails: Show error toast, keep existing photo if any, don't block form save
  2. Food log deleted: Navigate back to diary, show success toast
  3. Concurrent edit: Use updated_at timestamp to detect conflicts
  4. Date change: Moving log to different day updates diary for both old and new dates
  5. Linked Food update: Update Food record nutrition data but NOT other logs using that food
  6. No photo: Diary row shows no thumbnail, edit page shows "Add photo" placeholder
  7. Large photo files: Compress/resize on upload (match WeightLog behavior, max ~2MB)
  8. Navigate away unsaved: Show confirmation dialog (matching EditWeight pattern)
  9. Invalid nutrition values: Client-side validation: non-negative numbers, max reasonable values
  10. Meal type change: Log moves to different meal section in diary
  11. Authorization: Users can only edit their own logs — backend returns 403 for other users' logs
